# ADR-006：多客户端架构与信任边界（网页账号记忆 / Bitwarden 式自动填充）

> 目标：让 Vaultly 具备「浏览器里自动记忆 / 自动填充账号密码」的能力，
> 同时不破坏两条既有底线：**无服务器**（BYO WebDAV）与**字段级端到端加密**。
>
> 架构路线已定：**方案 B（宿主解密）**——密钥与解密永远留在 App/常驻宿主内，
> 浏览器扩展只做 DOM 识别与填充，通过 native messaging 按需索取最小数据。

---

## 0. 结论速览

| 决策点 | 结论 |
|---|---|
| 扩展侧是否解密 | **否**（方案 B）。扩展只拿「按需、最小」的明文字段 |
| 密钥层次 | 重构为 **DEK/KEK 两层**：随机数据密钥加密数据，主密码只派生包装密钥 |
| 口令校验哈希 | 废弃 `sha256(password‖salt)`，改为 Argon2id 派生后 **HKDF 切半**（加密半 / 校验半） |
| 同步删除 | 引入**墓碑**（deletedAt），修复「删除后合并复活」 |
| 加密核心复用 | 抽 `packages/vaultly_core`（纯 Dart，无 Flutter 依赖） |
| 移动端填充 | 不做扩展。Android 用系统 AutofillService，iOS 用 Credential Provider（Phase 1） |
| 云端备份格式 | **维持 v2 信封不变**（已稳定、有测试钉死）；DEK 只用于本地与宿主 |
| 常驻宿主 | Flutter 桌面 App（托盘常驻）+ native messaging，直接复用 vaultly_core |

## 1. 背景与问题定义

「Bitwarden 式网页账号记忆」拆开是三件事：

1. **浏览器扩展**——识别网页登录表单、提供保存/填充 UI（TS/JS，无法用 Flutter 写）
2. **一个能响应扩展请求的常驻宿主**——持有密钥、执行加解密、匹配条目
3. **App 内加密核心**——已有，但按多客户端标准有 4 个缺口（§3）

核心张力：扩展运行在**最不可信的运行时**（网页内容可诱导、恶意扩展泛滥），
而我们的威胁模型假设「密钥不出可信边界」。方案 B 正是为划清这条边界。

### 为什么选方案 B（宿主解密）而不是 A（扩展自解密）

| | A：扩展自解密（Bitwarden 桌面式） | **B：宿主解密（1Password 桌面式）** |
|---|---|---|
| 密钥所在 | 浏览器进程 | App/宿主进程 |
| 需要在 JS 重写的部分 | 全部加密、KDF、合并逻辑 | 零（IPC 消息即可） |
| 攻击面 | 扩展漏洞 = 全库泄露 | 扩展漏洞最多拿到单次请求返回的字段 |
| 与现有代码兼容 | 需 Dart→TS 移植加密，双实现漂移风险 | vaultly_core 原样复用 |
| 代价 | 无常驻进程依赖 | 用户需保持宿主运行（托盘，内存占用可控） |

选 B 的决定性理由：**加密代码只存在一份（Dart）**。方案 A 意味着 Argon2id/GCM/合并
逻辑在 TS 再实现一遍并永久保持同步——这正是本仓库刚修掉的「备份不带盐」这类
「两处实现漂移」事故的温床。

## 2. 信任边界与威胁模型（方案 B）

```
不可信区                可信区（密钥永不出）
┌──────────────┐  IPC  ┌─────────────────────────┐
│ 浏览器扩展    │──────▶│ 常驻宿主（Flutter 桌面）  │
│  · DOM 识别   │ 请求   │  · 会话密钥（内存）       │
│  · 表单填充   │◀──────│  · DEK 解包 / 字段解密    │
│  · 恶意页面 ⚠ │ 最小明文│  · 条目匹配打分          │
└──────────────┘       └──────────┬──────────────┘
                                  │ 复用
                       ┌──────────▼──────────────┐
                       │ vaultly_core（纯 Dart）  │
                       │ crypto / model / merge   │
                       └─────────────────────────┘
```

**规则**（违反任何一条即方案失败）：

1. 密钥（masterSecret / DEK / KEK）只在宿主进程内存中；IPC 永不传输密钥或密文库
2. 扩展每次请求只拿**当时需要**的字段（列表请求只回 id/标题/用户名/uri；
   密码只在用户点击填充那一刻、且仅回所请求的那一条）
3. 宿主验证调用方身份：native messaging 的 origin = 扩展 ID，
   只允许登记过的扩展 ID 连接；一次只允许一个扩展连接
4. 网页内容是不可信输入：扩展的解析代码禁止 innerHTML / eval，
   宿主对 IPC 消息做防御性校验（长度上限、类型白名单）
5. 宿主锁定 = 拒绝一切填充请求；自动锁定策略与 App 一致（复用 auto_lock_service 语义）
6. 填充动作必须由用户手势触发；host 与条目 uri 不匹配时要求显式确认

**残余风险**（明示接受）：宿主进程被本地恶意软件注入 → 密钥可被窃取。
这与 Bitwarden/1Password 相同，属于「本机已被攻破」场景，超出本项目威胁模型。

## 3. 前置重构：进入多客户端前必须完成的 4 件事

按依赖排序。R1/R2 是安全修正（不依赖扩展，随时可做），R3 是正确性前提，
R4 是工程前提。

### R1 口令校验哈希加固（P0，安全）

现状（crypto_service.dart:130 `deriveVerificationHash`）：
`sha256(password ‖ salt)` 落在安全存储 `master_password_hash`。
sha256 是快速哈希——安全存储一旦泄露（root / 备份提取 / 新增的 keyTag 通道拓宽了
落盘面），离线爆破主密码零成本。

**目标设计**（一次 Argon2id，HKDF 切半，避免跑两次 64MB KDF）：

```
masterSecret = Argon2id(password, salt)            // 32B，现行 deriveKeyWithArgon2id
authKey      = HKDF-SHA256(masterSecret, info:"vaultly/auth")    // 32B 落盘做校验
kek          = HKDF-SHA256(masterSecret, info:"vaultly/kek-wrap") // 32B 见 R2
```

- 落盘的校验值改为 `authKey`；HKDF 的域分离保证校验半不能反推加密半
- **迁移**：解锁时先验旧 sha256（老用户）→ 成功后立刻改写为新格式 + 升级
  `master_kdf_params` 版本号；失败次数计入既有防爆破计数器
- 上一轮加入的 `currentKeyTag()`（备份过期检测）继续有效：它是对落盘校验值的再哈希，
  校验值换了它跟着换，语义不变（测试 backup_freshness_test 已覆盖「解锁不变、改密必变」）

### R2 DEK/KEK 两层密钥（P0，改密体验与生物识别的地基）

现状：主密码派生密钥**直接**加密每个字段；改密 = 全量重加密重写
（vault_notifier.dart:70 rotateKey），生物识别靠 `biometric_encryption_key`
明文密钥存安全存储（auth_service.dart）。

**目标密钥层次**：

```
DEK（随机 32B，诞生即落库加密数据）
 ├── KEK 包装：AES-GCM(DEK, KEK = HKDF(masterSecret, info:"vaultly/kek-wrap"))
 └── 生物识别包装：AES-GCM(DEK, keystore 密钥)   // 替代现在的明文存 key
改主密码   = 重新包装 DEK（毫秒级），数据不动
解锁       = masterSecret → 解包 DEK → 字段解密（字段解密代码一行不改）
```

- `biometric_encryption_key` 从「明文密钥」变为「被 keystore 包装的 DEK」，
  消除「安全存储即密码等价物」的问题
- **迁移**：解锁时若发现旧格式（无 wrapped DEK）→ 用旧路径解出数据 → 生成 DEK
  → 全量重加密一次 → 写入 wrapped DEK → 删除旧校验路径。一次性，幂等，失败不动原数据
- **云端备份格式 v2 不动**：备份仍用「主密码 + 文件头参数」派生的密钥整包加密。
  理由：v2 刚发布且被 backup_envelope_test 钉死；备份是整包 GZIP，
  重新加密成本本来就低，DEK 的收益（改密免重加密）在备份场景不存在
  （改密后仍需重上传使云端与当前密码一致，keyTag 机制已覆盖）。
  「信封里带 wrapped DEK」作为备选被否：多设备各自 DEK 会让信封语义复杂化，
  换来的只是省一次整包加密

### R3 同步墓碑（P0，多端正确性）

现状：mergeVaultEntries 是 LWW 并集，删除只存在于本地内存——
任何一次「合并并上传」都会让已删条目复活。单端时是烦恼，双端时是数据正确性 bug。

**设计**：

- 条目增加 `deletedAt: DateTime?`（不可变模型，copyWith 维护）
- 删除 = `copyWith(deletedAt: now)`，仍参与同步；UI 层过滤 `deletedAt != null`
- 备份数据 `entries` 包含墓碑条目（字段原样保留）；加载/展示侧过滤
- 合并规则：一方 deletedAt 更新 → 删除胜出（墓碑也是 LWW，防止「旧副本回写复活」）
- 30 天后物理清除（上传时顺带过滤超龄墓碑）
- schema 版本：备份数据内部 `version: 1 → 2`，旧版本读取方忽略未知字段不受影响

### R4 抽出 vaultly_core（P1，工程前提）

- 新建 `packages/vaultly_core`：crypto_service、KdfParams/EncryptedEnvelope、
  vault 领域模型、字段级加密策略、vault_merge、（新增的）墓碑与匹配打分
- 约束：**零 Flutter 依赖**（可跑纯 Dart VM 测试），App 与桌面宿主共用
- App 侧改为依赖该包，现有 86 项测试迁移后作为回归门

## 4. 组件设计

### 4.1 桌面宿主（方案 B 的「可信区」）

- Flutter 桌面 App（Windows/macOS/Linux），托盘常驻，锁定 UI 与移动端一致
- 启动时向系统注册 native messaging 宿主：
  Windows 注册表 `HKCU\Software\Google\Chrome\NativeMessagingHosts\com.vaultly.host`、
  macOS/Linux 写 manifest json；允许的 origin = 登记的扩展 ID 列表
- 进程模型：常驻但不持密钥——锁定态内存里只有 wrapped DEK；
  解锁后 DEK 才解包进内存，auto_lock 到期立即清除
- 复用：auth/crypto/merge/vault 全部来自 vaultly_core；
  WebDAV 同步逻辑原样复用（宿主与手机各自上传，云端取最新，无需新协议）

### 4.2 IPC 协议（native messaging，最小命令集）

```
// 请求 → 响应，均为 JSON，单帧 ≤ 1MB（浏览器 native messaging 硬限制）
ping                    → { ok, version, locked }
status                  → { locked, keyTagFingerprint? , lastSyncAt? }
list-logins { uri }     → { items: [ { id, title, username, uriScore } ] }   // 无密码
get-credential { id, uri, reason: "fill" | "reveal" }
                        → { username, password, totp? , }
lock                    → { ok }
```

安全细则：

- `get-credential` 的 `uri` 由宿主**重新**与条目 uri 匹配打分（不信任扩展的匹配结果），
  低于阈值拒绝或要求确认；`reason: "reveal"` 时在宿主侧弹确认框
- 响应不含完整条目 JSON，字段白名单硬编码
- 每次调用记审计日志（时间、扩展请求的 uri、命中条目 id），本地可查看

### 4.3 浏览器扩展（不可信区，TS/JS）

- Manifest V3；content script + background service worker
- 表单识别启发式：`input[type=password]` 邻近的 username 字段推断、
  shadow DOM 递归、同源 iframe 逐帧处理；**不做**自动提交、不动隐藏表单
- 保存捕获：检测到「提交后新密码」→ 弹条目保存/更新询问 → 经 IPC 交给宿主加密落库
  （扩展拿到的新明文仅存活到发送完成，不落扩展存储）
- 填充：只填用户点击的 tab/弹窗对应的帧；先比对页面 host 与宿主返回的 uri 匹配分
- CSP：无远程代码、无 innerHTML；与宿主之外的任何域无通信

### 4.4 移动端自动填充（Phase 1，先于扩展交付）

- Android：`AutofillService` + `AutofillDataset`，启发式与扩展共享同一「匹配打分」
  纯 Dart 模块（vaultly_core 内），UI 用 Flutter 的 autofill 钩子 + 原生 service 壳
- iOS：AutoFill Credential Provider extension，App Group 共享加密库，
  身份验证复用 local_auth 流程
- 这是**纯 App 内改动**，不依赖宿主与扩展，性价比最高，先做

## 5. 数据模型与协议变更汇总

| 变更 | 位置 | 兼容性 |
|---|---|---|
| `LoginEntry` 增加 `uris: List<UriMatch>`（默认空） | vaultly_core | 旧备份读取忽略缺失字段，天然兼容 |
| 条目增加 `deletedAt`，备份内 version: 2 | vaultly_core + webdav | 旧版 App 读新备份会**把墓碑当活条目展示** → 升级提示文案注明；不做双向兼容开关 |
| 本机校验哈希 / wrapped DEK 新键 | 安全存储 | 首次解锁自动迁移，幂等 |
| IPC 协议 | 新增 | 无存量 |

## 6. Phase 计划与验收门

| Phase | 内容 | 验收 |
|-------|------|------|
| P1 | R1 + R2（校验哈希、DEK/KEK，含迁移与测试） | 现有 86 测试全绿；新增迁移测试：老格式解锁→自动升级→数据无损；改密仅重包装；生物识别走 DEK 包装路径 |
| P2 | R3 墓碑 + 备份 version 2 + keyTag 兼容性回归 | 删除→合并→上传→恢复链路删除不复活；backup_envelope_test 扩展覆盖 |
| P3 | R4 vaultly_core 抽包 | App 依赖切换后 analyze 0、全测试绿；core 包在纯 Dart VM 下测试通过 |
| P4 | Android AutoFill（iOS 视设备情况跟进） | Chrome/系统浏览器登录页出现 Vaultly 填充建议；锁定态不出数据 |
| P5 | 桌面宿主 + native messaging（status/list/get/lock） | 协议集成测试；锁定态 get-credential 必须拒绝 |
| P6 | 浏览器扩展（识别/捕获/填充） | 对 GitHub 等真实站点手动冒烟；恶意页面注入用例（script 注入/隐藏表单）全部拒绝 |

回滚方案：每个 Phase 独立分支 + `--no-ff` 合并；P1/P2 涉及数据迁移，
迁移代码必须幂等且失败不落盘（沿用 vault_service「解密失败不清空内存态」原则）。

## 7. 非目标

- 自建同步服务器 / 账号体系 / 组织与分享（保持 BYO WebDAV；若未来要做，另立 ADR）
- 团队/家庭共享、服务端推送（Bitwarden 的 server 能力均不引入）
- Firefox/Safari 扩展（P6 先 Chromium 系；协议与宿主已按多浏览器设计，扩展层后补）
- 扩展内离线解锁（密钥进浏览器违背方案 B）
