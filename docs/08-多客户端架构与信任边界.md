# ADR-006：多客户端架构与信任边界（网页账号记忆 / Bitwarden 式自动填充）

> 目标：让 Vaultly 具备「浏览器里自动记忆 / 自动填充账号密码」的能力，
> 同时不破坏两条既有底线：**无服务器**（BYO WebDAV）与**字段级端到端加密**。
>
> 架构路线：**方案 B（宿主解密）**——密钥与解密永远留在 App/常驻宿主内，
> 浏览器扩展只做 DOM 识别与填充，通过 native messaging 按需索取最小数据。
>
> v1.1 修订：补齐写路径、宿主进程模型、schema 版本策略、iOS 边界决策，
> 并新增 R0（原子写）与 6 条跨阶段硬约束。修订依据见 §10。

---

## 0. 结论速览

| 决策点 | 结论 |
|---|---|
| 扩展侧是否解密 | **否**（方案 B）。扩展零加密、零匹配逻辑 |
| 密钥层次 | **DEK/KEK 两层**：随机数据密钥加密数据，主密码只派生包装密钥 |
| 口令校验哈希 | 废弃 `sha256(password‖salt)`，改 Argon2id + **HKDF 域分离切半** |
| 存储写入 | **新增 R0**：写前备份 + 双 key 原子写（原技术债 A3 提前，R2 迁移的前提） |
| 同步删除 | **墓碑** `deletedAt` + **回收站 UI**（含恢复/清空） |
| 扩展写路径 | **必须提供** save/update/dismiss（「记忆」的另一半，v1.0 遗漏） |
| 加密核心复用 | 抽 `packages/vaultly_core`（纯 Dart，无 Flutter 依赖） |
| 移动端填充 | Android AutofillService（安全）；iOS 需先决策元数据边界（§4.5） |
| 云端备份格式 | **信封维持 v2**；负载升到 `v2`（含墓碑）并加 `schemaVersion` 校验（fail-closed） |
| 常驻宿主 | Flutter 桌面（六个平台 target 均已存在）+ daemon/shim 双进程模型 |
| Web 版客户端 | **不做**（浏览器内无法保证密钥边界） |
| Passkey | **暂不做**（理由见 §9） |

## 1. 背景与问题定义

「Bitwarden 式网页账号记忆」拆开是三件事：

1. **浏览器扩展**——识别网页登录表单、提供保存/填充 UI（TS/JS，无法用 Flutter 写）
2. **一个能响应扩展请求的常驻宿主**——持有密钥、执行加解密、匹配条目
3. **App 内加密核心**——已有，但按多客户端标准有 5 个缺口（§3）

注意第 1 条里有**两个方向**：读（填充）和**写（记忆）**。v1.0 只设计了读路径，
而用户要的「账号密码记忆」主体在写路径上（§4.2 已补）。

### 为什么选方案 B 而不是 A（扩展自解密）

| | A：扩展自解密（Bitwarden 桌面式） | **B：宿主解密（1Password 桌面式）** |
|---|---|---|
| 密钥所在 | 浏览器进程 | App/宿主进程 |
| 需在 JS 重写的部分 | 全部加密、KDF、合并逻辑 | 零（IPC 消息即可） |
| 攻击面 | 扩展漏洞 = 全库泄露 | 扩展漏洞最多拿到单次请求的字段 |
| 与现有代码兼容 | 需 Dart→TS 移植加密，双实现漂移风险 | vaultly_core 原样复用 |
| 代价 | 无常驻进程依赖 | 需常驻宿主（托盘，内存占用可控） |

决定性理由：**加密代码只存在一份（Dart）**。方案 A 意味着 Argon2id/GCM/合并逻辑
在 TS 再实现一遍并永久保持同步——这正是本仓库刚修掉的「备份不带盐」这类
「两处状态漂移」事故的温床。

## 2. 信任边界与威胁模型

```
不可信区                可信区（密钥永不出）
┌──────────────┐  IPC  ┌─────────────────────────┐
│ 浏览器扩展    │──────▶│ 常驻宿主 daemon          │
│  · DOM 识别   │ 请求   │  · 会话密钥（内存）       │
│  · 表单填充   │◀──────│  · DEK 解包 / 字段解密    │
│  · 恶意页面 ⚠ │ 最小明文│  · 条目匹配打分          │
└──────────────┘       └──────────┬──────────────┘
                                  │ 复用
                       ┌──────────▼──────────────┐
                       │ vaultly_core（纯 Dart）  │
                       │ crypto / model / merge   │
                       └─────────────────────────┘
```

**硬规则**（违反任何一条即方案失败）：

1. 密钥（masterSecret / DEK / KEK / 上传用派生密钥）只在宿主内存；
   IPC 永不传输密钥或密文库
2. 扩展每次只拿**当时需要**的字段：列表请求只回 id/标题/用户名；
   密码只在用户点击填充那一刻、且只回所请求的那一条
3. 宿主校验调用方：allowed extension ID 白名单（origin pinning）；
   一次只允许一个扩展连接
4. 网页内容是**不可信输入**：扩展解析禁用 innerHTML / eval；
   宿主对 IPC 消息做防御性校验（长度上限、类型白名单、id 必须存在于当前库）
5. **不跨源 iframe 填充**：只填顶层文档与同源帧，防诱导填充（clickjacking）
6. 填充必须由**用户手势**触发；host 与条目 uri 匹配分低于阈值时要求显式确认
7. 宿主锁定 = 拒绝一切填充与写入；锁定态只允许 `status`（回 `{locked:true}`）
8. 宿主复用 App 的**失败计数与锁定策略**（5 次/5 分钟、10 次/30 分钟），
   不得提供比 App 更快的密码猜测通道
9. 审计日志只记 **eTLD+1**（不记完整 URL，否则等于在本地建浏览历史库），
   限额轮转、可关闭、可清空

**残余风险（明示接受）**：宿主进程被本地恶意软件注入 → 密钥可被窃取。
与 Bitwarden/1Password 相同，属「本机已被攻破」场景，超出本项目威胁模型。

## 3. 前置重构（按依赖排序）

R0 → R1 → R2 有严格依赖；R3、R4 可并行推进。

### R0 存储写入加固（P0，R2 的前提）

现状：`vault_data` 单 key 全量 JSON，**无写前备份、无原子写**
（vault_service.dart:101-117；原登记为技术债 A3）。单机时是「小概率丢库」，
而 R2 的迁移是**一次性全量重写**——中途崩溃/断电就是不可恢复的数据损失。

**决策**：把 A3 从技术债提升为 R0 前置项。

- 写前留存上一份：`vault_data.prev`（或带时间戳的滚动 2 份）
- 原子写：先写临时 key → 校验可解析 → 再切换主 key → 最后删旧
- 启动加载：主 key 解析/解密失败时自动尝试 `.prev` 并在 UI 明确告知「已从备份恢复，
  请检查最近一次修改」
- 沿用既有原则：解密失败**不清空内存态**（vault_service.dart:89-95 已如此）

### R1 口令校验哈希加固（P0，安全）

现状：`sha256(password ‖ salt)` 落在安全存储（crypto_service.dart:130
`deriveVerificationHash`）。sha256 是快速哈希——安全存储一旦泄露，离线爆破零成本。

**目标**（一次 Argon2id，HKDF 切半，避免跑两次 64MB KDF）：

```
masterSecret = Argon2id(password, salt)                          // 32B，不变
authKey      = HKDF-SHA256(masterSecret, info:"vaultly/auth")     // 32B 落盘做校验
kek          = HKDF-SHA256(masterSecret, info:"vaultly/kek-wrap") // 32B 见 R2
keyTag       = HKDF-SHA256(masterSecret, info:"vaultly/key-tag")  // 备份过期检测用
```

- HKDF 自实现（RFC 5869，约 20 行，基于 `crypto` 包的 Hmac），**不新增依赖**；
  必须带 RFC 5869 官方测试向量
- **迁移**：先按旧 sha256 校验（老用户）→ 成功后改写为 `authKey` 并升级
  `master_kdf_params` 版本；失败计入既有防爆破计数器
- keyTag 的来源从「落盘校验值的再哈希」改为直接 HKDF 派生。
  理由见 §3.5 约束 C1：校验值会因 R1 而变，若 keyTag 仍基于它，
  升级当天所有用户都会看到「云端备份已过期」的误报

### R2 DEK/KEK 两层密钥（P0）

现状：主密码派生密钥**直接**加密每个字段；改密 = 全量重加密重写
（vault_notifier.dart:70）；生物识别把**明文密钥**存安全存储
（auth_service.dart `_keyBiometricEncryptionKey`）。

**目标密钥层次**：

```
DEK（随机 32B，加密全部字段）
 ├── 主密码包装：AES-GCM(DEK, KEK = HKDF(masterSecret, "vaultly/kek-wrap"))
 ├── 生物识别包装：AES-GCM(DEK, keystore 密钥)
 └── 【必须】上传用密钥也一并包装：AES-GCM(backupKey, keystore 密钥)
改主密码 = 重新包装 DEK（毫秒级），数据不动
解锁     = 解包 DEK → 字段解密（字段解密代码一行不改）
```

**⚠ 生物识别会话必须仍能上传**（v1.0 遗漏的坑）：
云端备份按设计仍由「主密码派生密钥」加密（见 §5），而 DEK 无法替代它。
若生物识别只包装 DEK，则生物识别解锁后 `_masterPassword == null` 且
`backupKey` 不存在 → **上传功能静默失效**。因此生物识别启用时必须同时包装
`backupKey`，并在改密后一并重包装。

**由此确定的语义**（写进 UI 文案）：

| 会话来源 | 能上传 | 能恢复本机备份 | 能恢复**其他设备**的备份 |
|---|---|---|---|
| 主密码解锁 | ✅ | ✅ | ✅ |
| 生物识别解锁 | ✅（用包装的 backupKey） | ✅ | ❌ 需改用主密码解锁 |

这与 v4.0.1 现状一致（`_resolveBackupKey` 在参数不一致且无明文口令时明确提示
「请改用主密码解锁」），行为可预期。

**迁移**：解锁时发现旧格式（无 wrapped DEK）→ 走旧路径解出全部条目 →
生成 DEK → 全量重加密 → 写 R0 的原子写 → 写入 wrapped DEK → 删除旧校验路径。
幂等、可重入、失败不落盘。

### R3 同步墓碑 + 回收站（P0，多端正确性）

现状：`mergeVaultEntries` 是 LWW 并集且**明确不删除任何一侧条目**
（vault_merge.dart:40,51-62）——删除只存在于本地内存，任何一次合并都会让已删条目复活。

**设计**：

- 条目增加 `deletedAt: DateTime?`；删除 = `copyWith(deletedAt: now)`，仍参与同步
- 备份 `entries` 包含墓碑条目；加载/展示侧过滤 `deletedAt != null`
- 合并：墓碑同样走 LWW；一方 deletedAt 较新 → 删除胜出
- **回收站 UI（v1.0 遗漏）**：设置或条目列表入口，可查看已删条目、恢复、清空；
  30 天后物理清除（上传时顺带过滤超龄墓碑）
- 备份数据内部 `version: 1 → 2`；读取方必须按 §5 的 fail-closed 规则处理

### R4 抽出 vaultly_core（P1，工程前提）

- `packages/vaultly_core`：crypto（KdfParams/EncryptedEnvelope/HKDF）、领域模型、
  字段级加密策略、merge、uri 匹配打分、墓碑规则
- 约束：**零 Flutter 依赖**，可在纯 Dart VM 下 `dart test`
- 新增依赖：eTLD+1 规范化需要 Public Suffix List（Dart 有 `publicsuffix` 包）；
  这是匹配打分的正确性前提（`evil-github.com` 不得匹配 `github.com`）
- App 侧改为路径依赖该包；现有 86 项测试迁移后作为回归门
- CI 增加 core 包独立测试 job

### 3.5 跨阶段硬约束（v1.1 新增）

| # | 约束 | 违反后果 |
|---|---|---|
| **C1** | R1/R2 迁移**不得改变本机 salt 与 masterSecret**；keyTag 一律由 masterSecret 派生（`info:"vaultly/key-tag"`） | 升级当天所有设备误报「云端备份已过期」，用户被引导去无意义地重传 |
| **C2** | 备份/存储读取一律 **fail-closed**：`schemaVersion` 高于自身认知时拒绝处理并提示升级，**绝不静默丢弃未知字段** | 旧版读到含墓碑的备份 → 丢掉 `deletedAt` 后回传 → 已删除的密码永久复活 |
| **C3** | 迁移路径必须幂等 + 原子（依赖 R0），且在 UI 有明确状态（「正在升级本地数据…」） | 迁移中途失败 → 库不可读 |
| **C4** | 任何密钥层次变更都要成对更新「主密码包装」与「生物识别包装」 | 生物识别会话功能静默失效（如 R2 的上传） |
| **C5** | merge 必须是确定性的：同 `updatedAt` 时按**墓碑优先 → 内容指纹**裁决（仅按 `id` 排序无法区分同一条目的两个版本），结果按 `updatedAt` 倒序 + `id` 升序收尾；现行「保留本地」使结果依赖参数顺序 | 两端反复同步结果不一致、条目来回抖动 |
| **C6** | 新增字段必须能被旧备份缺省读取（缺失 → 默认值），不得让旧备份解析失败 | 用户的历史备份打不开 |

## 4. 组件设计

### 4.1 宿主进程模型（v1.1 补充）

v1.0 写的「托盘常驻」过于笼统，实际约束：

- **native messaging 是按连接 spawn 进程的**——Chrome 每次 `connectNative` 会起一个新
  进程。若把这个进程当作宿主，则每次连接都要重新解锁，不可用
- 因此采用 **daemon + shim 双进程**：
  - `vaultly-host`（shim，native messaging 端点）：极薄，只做 stdio↔本地 socket 转发
  - `vaultly-daemon`（常驻）：持有会话密钥与锁定状态；shim 发现 daemon 不在则拉起
- **socket 加固**：Windows 命名管道用当前用户 SID 的 ACL；
  macOS/Linux 用用户私有目录下的 unix socket（`chmod 600` + peer credential 校验）。
  绝不开 TCP 端口
- **注册方式**：Windows `HKCU\Software\Google\Chrome\NativeMessagingHosts\com.vaultly.host`；
  macOS/Linux 写 manifest json（`allowed_origins` 限定扩展 ID）
- macOS 注意：Chrome 无法直接启动 GUI app，宿主必须是 **agent**（LSUIElement）
  或以非 GUI 进程形态分发；这是 P5 的主要工程风险（§7）
- 宿主 UI 复用 App 的解锁页与自动锁定策略；托盘菜单提供锁定/解锁/打开主界面
- 宿主逻辑必须能在**无 GUI 的 CLI 模式**下跑（便于协议与迁移的自动化测试）

### 4.2 IPC 协议（读 + 写，v1.1 补齐写路径）

单帧 ≤ 1MB（native messaging 硬限制），JSON。

```
// —— 读路径 ——
ping                     → { ok, version, locked }
status                   → { locked, keyTag, lastSyncAt }
list-logins { uri }      → { items: [ { id, title, username, uriScore } ] }   // 无密码
get-credential { id, uri, reason: "fill" | "reveal" }
                         → { username, password, totp, totpRemainSeconds }

// —— 写路径（「记忆」的主体，v1.0 遗漏）——
detect-change { uri, kind: "new" | "update" | "unknown" }
                         → { candidateId?, existingTitle? }   // 宿主判定新建 or 更新
save-credential { uri, username, password, title?, targetId? }
                         → { id, action: "created" | "updated" }
dismiss-save { uri }     → { ok }        // 用户选择「不保存」，记入忽略名单

// —— 会话 ——
lock                     → { ok }
request-unlock           → { ok }        // 唤起宿主解锁窗口，扩展只能请求、不能解锁
```

安全细则：

- `get-credential` 的 `uri` 由宿主**重新**与条目 uri 匹配打分（不信任扩展的匹配结果），
  低于阈值拒绝或要求确认；`reason:"reveal"` 在宿主侧弹确认框
- 响应字段**白名单硬编码**，不含完整条目 JSON
- `save-credential` 是唯一写入路径：宿主负责加密落库（复用 VaultService），
  并写审计日志；扩展转发的新密码仅存活到发送完成，**不落扩展任何存储**
- TOTP 有 30 秒时效：扩展可用 `totpRemainSeconds` 决定是否重新请求；
  不做长连接推送（避免常驻通道扩大攻击面）
- 全部调用记审计日志（时间、命令、eTLD+1、命中 id），本地可查可清

### 4.3 浏览器扩展（不可信区，TS/JS）

- Manifest V3；content script + service worker
- **零加密、零匹配逻辑**：所有判断由宿主做，扩展只做「DOM ↔ IPC」的翻译层
- 表单识别启发式：`input[type=password]` 邻近 username 推断、shadow DOM 递归、
  **仅同源 iframe**、跨源帧不填（规则 5）
- 保存捕获：提交后检测新密码 → `detect-change` → 弹「保存/更新/不保存」
  → 相应 IPC；两密码框（改密码场景）走 `kind:"update"`
- 填充：只填用户点击的 tab/帧；先核对宿主返回的 uriScore
- CSP：无远程代码、无 innerHTML，与除宿主外的任何域无通信
- **必须固定 manifest 的 `key`**，否则扩展 ID 会变，origin pinning 失效
- 锁定态：显示「在 Vaultly 桌面端解锁」，并提供 `request-unlock` 唤起宿主窗口

### 4.4 移动端自动填充

**Android（Phase P4）：无信任边界冲突。** AutofillService 运行在 App 自己的进程内，
数据集由宿主侧（应用内）生成；锁定态只提供「解锁 Vaultly」一项建议。
启发式匹配复用 vaultly_core 的打分模块。

**iOS：必须先做架构决策（v1.1 新增）。** Credential Provider 是**独立进程**，
通过 App Group 共享数据；系统 QuickType 要在扩展未运行时列出候选，因此必须向
`ASCredentialIdentityStore` 提交 **(域名, 用户名) 明文元数据**。这突破了
「密钥不出单进程」的边界（元数据在系统凭据库中，受设备锁加密保护，但已不在我们的密文里）。

| 选项 | 结论 |
|---|---|
| A. 接受元数据交系统，换取 iOS 自动填充 | **推荐**——这是平台唯一可行方式，Bitwarden/1Password 均如此；需在文档与首次启用时明示 |
| B. 不交元数据 → iOS 只能手动复制粘贴 | 保留边界但体验残缺，可选择只做 Android |

决策待 PM 确认后写入本文档；在确认前 iOS 自动填充**不排期**。

### 4.5 明确不做 Web 版客户端

仓库存在 `web/` target，但浏览器内无法保证密钥边界（无安全存储、JS 内存可被
任意扩展/脚本读取）。Web 版仅作为文档站或只读演示的可能，**不作为客户端**。

## 5. 数据模型与兼容性

| 变更 | 位置 | 兼容性 |
|---|---|---|
| `LoginEntry.url`（单字段）→ `uris: List<UriMatch>` | vaultly_core | **迁移规则**：`uris = [UriMatch(url, mode: domain)]`；保留 `url` 字段写入以兼容旧版读取；`UriMatch` 含 `mode: domain\|host\|startsWith\|regex\|exact` |
| 条目增加 `deletedAt`；本地负载 `schemaVersion: 1→2`；备份负载 v1→v2 | vaultly_core + webdav | 按 **C2** fail-closed：读取方校验 `schemaVersion`，未知版本拒绝处理并提示升级。备份 v2 把条目放在 `vault.entries`，旧版取不到顶层 `entries` 会拒绝应用（P3 落地记录 3） |
| 本机 `authKey` / `wrappedDek` / `wrappedBackupKey` | 安全存储 | 首次解锁自动迁移，幂等（R0 保证原子） |
| `keyTag` 改为 HKDF(masterSecret, "vaultly/key-tag") | 安全存储 + sync repo | 语义不变（解锁不变、改密必变），实现来源变化；backup_freshness_test 需同步调整 |
| IPC 协议（读+写） | 新增 | 无存量 |

**云端备份信封维持 v2 的理由**：v2 刚发布且被 backup_envelope_test 钉死；备份是整包
GZIP，重加密成本本来就低，DEK 的收益（改密免重加密）在备份场景不存在——改密后仍需
重上传使云端与当前密码一致（keyTag 机制已覆盖）。「信封内带 wrapped DEK」被否：
多设备各自 DEK 会让信封语义复杂化，只换来省一次整包加密。

**版本窗口的操作规则**：格式升级的版本发布时，必须提示用户**先把所有设备升级到
同一版本再同步**（C2 只能保护新版本，旧版本无法改造）。

**注意**：P3 已实装格式升级，因此「所有设备先升级」这条规则从 P3 起真正生效——
旧版本读到含墓碑的备份会拒绝应用（结构性 fail-closed），但它**上传**时仍会写出
不含墓碑的 v1 备份（旧代码无法改造）。新版合并这种旧备份时，本地墓碑更「新」
因而胜出，删除不会被撤销；但从这份旧备份全新恢复的设备会缺少删除记录。

**P1 落地记录（迁移不可回退）**：迁移成功后会删除 `master_password_hash`
（sha256 弱哈希）——这正是 R1 的目的。代价是**降级回 v4.0.1 及更早版本后会认为
「未设置主密码」**，因此带此改动的版本只能前进、不能回退。确需回退时，
应先在旧版本仍可用时导出一份新格式备份。

**P2 落地记录**

1. **两把密钥必须分清**（R2 最容易搞错的地方）：
   - `encryptionKey` = **DEK** → 本地字段级加密
   - `backupKey` = **masterSecret** → 云端备份加密（必须能被别的设备用主密码解开）

   同步页原先把 `encryptionKey` 当备份密钥用。若不同步改掉，R2 之后**上传会写坏备份**
   （新备份不再能被其他设备解开）。已改为 `backupKey`，并在 `_resolveBackupKey`
   与 `_upload` 两处注明原因。
2. **生物识别项存的是 masterSecret**（不是 DEK）：它既能解包 DEK，又能在生物识别
   会话里继续加密云端备份（满足 §3 R2 的 F2 约束）。升级前存的本来就是
   masterSecret，因此**没有新增密钥种类**。
3. **迁移顺序**：`ensureDek` 先落盘包装好的 DEK → 保险库侧「用旧密钥读、用新密钥写」
   （`migrateTo` 必须 await，否则会出现「数据还没加载完就重加密」→ 空列表覆盖磁盘）
   → 失败则删除刚写的 wrappedDek 回滚，保持旧密钥体系，数据依然可读。
4. **改密不再全量重加密**：`AuthNotifier.changePassword` 不再发布新密钥触发
   `rotateKey`；DEK 不变，只重新包装。keyTag 仍会变 → 同步页照常提示
   「云端备份还是旧主密码加密的」。

**R2b（登记未做）**：本文档 §3 R2 写的「生物识别包装 = AES-GCM(DEK, keystore 密钥)」
需要平台通道才能真正落地（Android Keystore + `BiometricPrompt` CryptoObject、
iOS Keychain access control）。当前实现是把 masterSecret 放进
flutter_secure_storage（本身即受系统 keystore/keychain 保护），
**与升级前保护级别相同、没有退步，但也没有获得硬件绑定**。
真正的硬件绑定另立 R2b，需要原生代码与真机验证，不阻塞 P3 之后的桌面/扩展工作。

**P3 落地记录**

1. **删除 = 墓碑 + 刷新 `updatedAt`**（`markEntryDeleted`）。只写 `deletedAt`
   而不动 `updatedAt` 是最隐蔽的错误：LWW 会判旧副本更新，删除被静默撤销。
   同 ID 的删除与否、以及保留期，全部集中在 `vault_tombstone.dart`。
2. **两个列表必须分清**：`VaultState.entries` 是活跃条目（界面用），
   `allEntries` 含墓碑（持久化/合并/上传用）。同步侧原先读 `entries`，
   若沿用会让删除在云端消失——与 P2 的「两把密钥」是同类陷阱，
   已在服务层提供 `activeEntries` / `trashedEntries` 并把同步侧改为 `allEntries`。
3. **备份 v2 换了外层键名**（`entries` → `vault.entries`），这是对 §3 R3
   「version: 1 → 2」的加强：旧版本只认顶层 `entries` 且会静默忽略未知字段，
   若沿用同一键名，旧版会把墓碑当普通条目读出来再传回去，删除被永久抹掉。
   改成嵌套键后旧版取不到列表 → 报「格式不正确」并**拒绝应用**，
   属于结构性 fail-closed，比只加一个旧版根本不看的 `version` 字段更可靠。
4. **版本闸门在两侧都做**：本地存储 `schemaVersion` 高于自身时，
   既不解析也**不回退到写前备份**（否则等于把新数据静默换成旧快照），
   并置位禁止写回；备份侧抛 `BackupVersionException`，
   同步页把它转成带错误码的 `WebDAVException` 并**中止**——
   合并前的「拉取失败就按首次上传处理」那条兜底逻辑必须放过它，
   否则会用旧数据覆盖新备份。
5. **C5 确定性**：同 `updatedAt` 时先墓碑优先，再按内容指纹
   （`toJson` 序列化）裁决，结果与参数顺序无关；结果列表按
   `updatedAt` 倒序 + `id` 升序排序。旧实现在同时间戳时「保留本地」，
   两台设备交替同步会来回抖动。
6. **写前回读校验的连带修改**：写入时会顺带剔除超龄墓碑，
   因此 `_verifyPayload` 必须与**剔除后**的条数比较——否则每次保存都会被
   自己的校验判成坏数据（这条已用回归用例钉住）。
7. **保留期**：§7 开放问题 3（是否可配置）暂定**不可配置**，固定 30 天，
   仅在 `kTombstoneRetention` 一处定义。语义是「所有设备 30 天内至少上线一次」。
